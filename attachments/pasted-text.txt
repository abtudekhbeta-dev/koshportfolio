2. PATH — CORE DEFINITION
------------------------------------------------------------

Kosh has two separate historical portfolio concepts.

A. CURRENT MIX / HISTORICAL SIMULATION

Question:

"How would the portfolio I hold today have performed historically?"

This uses the current portfolio composition and applies it to historical data.

KEEP THIS.

B. PATH

Question:

"What did I actually own over time, based on my real trades, and how did that portfolio perform?"

Path reconstructs the investor's historical equity holdings based on the broker trade book.

KEEP THIS.

These must remain clearly separated in both implementation and UI.

Do not make the user think Current Mix and Path answer the same question.

------------------------------------------------------------
3. PATH — TRADE RECONSTRUCTION
------------------------------------------------------------

Path should reconstruct holdings chronologically from the broker trade book.

For each trade, preserve as much original information as available:

- symbol
- ISIN
- exchange
- date
- execution timestamp
- buy/sell
- quantity
- execution price
- broker trade ID
- broker order ID
- original source row

Do not unnecessarily normalize away useful broker information.

------------------------------------------------------------
4. DUPLICATE TRADE HANDLING — IMPORTANT
------------------------------------------------------------

Legitimate broker executions must never disappear because they happen to have the same:

- symbol
- date
- side
- quantity
- price

Example:

10:01
BUY
10 shares
₹100

10:02
BUY
10 shares
₹100

These are two legitimate trades and must remain two trades.

Preferred identity hierarchy:

1. Broker trade/execution ID
2. Broker order/execution identifier
3. Timestamp + symbol + side + quantity + price
4. Original source-row identifier as fallback

Do not perform aggressive deduplication.

Add regression tests.

------------------------------------------------------------
5. SAME-DAY TRADE ORDERING — IMPORTANT
------------------------------------------------------------

Do NOT force buys before sells.

If timestamps exist, process trades chronologically.

Example:

10:00 — SELL 100
14:00 — BUY 100

must be:

SELL → BUY

not:

BUY → SELL

Preferred order:

1. trade date
2. execution timestamp
3. broker/source row order if timestamp is unavailable

If timestamps are unavailable, preserve original broker row ordering where possible.

Add tests for:

- Buy → Sell same day
- Sell → Buy same day
- Buy → Sell → Buy same day
- multiple same-day trades

------------------------------------------------------------
6. MISSING TRADE PRICE — SIMPLE FALLBACK
------------------------------------------------------------

Sometimes the broker trade book does not contain an execution price.

In that case, Kosh may use:

THE SECURITY'S CLOSING PRICE ON THE TRADE DATE

as a reconstruction fallback.

This is acceptable and should remain.

Do NOT build a complicated confidence framework.

Internally distinguish:

ACTUAL EXECUTION PRICE

from:

ESTIMATED EXECUTION PRICE

When actual execution price is unavailable, mark the trade as estimated.

Use wording such as:

"Execution price unavailable; historical closing price used."

Do not imply that Kosh knows the exact execution price.

The fallback is acceptable for reconstructing the historical portfolio.

Do not unnecessarily prevent Path from working just because one trade lacks execution price.

------------------------------------------------------------
7. PATH — TWR
------------------------------------------------------------

The current TWR architecture is conceptually correct.

Preserve it unless a specific implementation bug is found.

TWR should answer:

"How well did my investment decisions perform, independent of how much money I added or removed?"

Verify that:

- additional capital does not artificially increase performance
- withdrawals do not artificially decrease performance
- internal buys/sells do not distort TWR
- daily returns are calculated correctly
- returns are properly chained
- monthly returns can be derived from the daily series
- yearly returns can be derived from the daily/monthly series

Do not replace a correct TWR implementation unnecessarily.

------------------------------------------------------------
8. PATH — XIRR
------------------------------------------------------------

This is a critical correction.

Do NOT automatically treat every:

BUY = negative cash flow
SELL = positive cash flow

and then label the result:

"Portfolio XIRR"

That is misleading because buys and sells are generally internal portfolio transactions.

For the current Path implementation:

IF ONLY THE BROKER TRADE BOOK IS AVAILABLE:

Use TWR as the primary portfolio performance metric.

Do not display a misleading "true XIRR".

If Kosh does not have reliable external portfolio cash-flow information:

- hide XIRR, OR
- clearly indicate that true XIRR cannot be calculated from the available information.

If actual external deposits/withdrawals are already available elsewhere in Kosh and can be reliably used, then calculate XIRR from those actual portfolio-level cash flows.

The key rule:

NEVER PRESENT A NUMBER AS TRUE XIRR IF THE UNDERLYING CASH FLOWS DO NOT SUPPORT THAT INTERPRETATION.

Do not build a complicated cash-accounting system just for this.

12. PATH — BENCHMARK
------------------------------------------------------------

Internal portfolio transactions such as:

BUY STOCK B

are investment decisions.

They are NOT external deposits or withdrawals.

Do not construct benchmark cash flows by treating every stock sale as investor withdrawal.

Where external portfolio cash-flow information exists, benchmark should reflect those external flows.

Otherwise, use a consistent TWR comparison.

Primary presentation:

PORTFOLIO TWR
vs
NIFTY TWR

and:

DIFFERENCE

Use a consistent return methodology.

If the portfolio uses price return, compare with a comparable benchmark.

If the portfolio is total-return adjusted and Nifty TRI is reliably available, use the corresponding total-return benchmark.

Do not mix price-return portfolio data with total-return benchmark data without explicitly explaining the difference.

Do not introduce unnecessary new data dependencies solely for benchmark complexity.
